## 확정된 결정

### 세 갈래가 다 살아있다

사용자가 팀에 재확인한 결과, API는 세 가지로 온다.

| 갈래 | `keyword` | `categoryId` | `radiusMeters` | PR |
|---|---|---|---|---|
| 카테고리 + 위치 | NULL | 있음 | 3000 | **PR 1** |
| 위치만 | NULL | NULL | 3000 | **PR 1** |
| 검색어만 | 있음 | NULL | **NULL (전국)** | PR 2 |

### PR 1 = A + B, PR 2 = FULLTEXT (완전히 독립)

두 PR은 **겹치지 않는다.** 검색어 갈래는 반경이 `null`이라 bbox를 만들 수 없어 A+B 효과가 **0**이고,
좌표 갈래는 `MATCH` 절이 없어 FULLTEXT 효과가 0이다. "PR1으로 일부 개선 후 PR2를 더한다"가 아니라
**서로 다른 병을 각각 고치는 것**이다.

- **A** — bounding box 선필터 + 위경도 인덱스
- **B** — 계단식 반경 (A 위에 얹는다. **B 단독은 의미 없다** — 반경은 `HAVING`에만 쓰여 스캔량을 못 줄인다)
- 버린 것: **C** SPATIAL(R-tree, 230ms 중 126ms만 잡음 · 스키마 변경 큼), **D** 지연 조인(B를 쓰면 의미 축소),
  **E** 기본 반경 축소(**결과가 바뀐다** — B가 같은 효과를 결과 변경 없이 낸다), **F** 캐시(원인을 안 고침)

## 구현 체크리스트

### 1. 마이그레이션 `V11__store_geo_index.sql`

`V10`이 마지막이다. **인덱스 2개**를 만든다.

```
idx_store_lat_lng      (latitude, longitude)               76.6MB
idx_store_cat_lat_lng  (category_id, latitude, longitude)  약 90MB
```

**둘 다 필요한 이유는 leftmost prefix다.** 위치만 오는 요청에는 `category_id` 조건이 없어
복합 인덱스의 첫 컬럼을 못 채운다. 반대로 카테고리 갈래에 `(latitude, longitude)`만 쓰면
로컬 0.18s ≈ 운영 300ms로 목표를 3배 넘긴다(실측).

- **멱등하게 쓴다** (AGENTS.md §11) — `information_schema`로 존재 확인 후 `PREPARE`.
  MySQL에 `CREATE INDEX IF NOT EXISTS`가 없어 재실행하면 "Duplicate key name"으로 기동이 죽는다
- 끝에 `ANALYZE TABLE store`
- 로컬 생성 시간 2.5초 + 약 3초. 온라인 DDL이라 중단은 없지만 **Flyway가 앱 기동 시 돌리므로
  첫 기동이 그만큼 늦어진다** — EB 헬스체크 타임아웃 확인할 것
- 기존 `idx_store_category_id`(67.2MB)는 복합 인덱스의 prefix라 중복이지만 **이번엔 건드리지 않는다**.
  `store`를 참조하는 매퍼가 8개라 별건으로 뺀다

### 2. 매퍼 `StoreMapper.xml` — bbox 조건 추가

**반드시 `<if>` 동적 SQL로 한다. 기존 NULL 가드 트릭 위에 얹지 말 것.**

```sql
-- 이렇게 하면 안 된다
AND (#{cond.radiusMeters} IS NULL OR s.latitude BETWEEN ... AND ...)
```

옵티마이저가 `3000 IS NULL`을 FALSE로 접어주기를 기대하는 형태다. 접히면 인덱스를 타고
안 접히면 풀스캔인데 **어느 쪽이든 결과는 똑같이 맞다.** 테스트로 안 잡히고 성능만 조용히 죽는다.

올바른 형태:

```sql
-- 6371000 은 아래 ACOS 식의 반지름과 같은 값이어야 한다
WHERE s.latitude  BETWEEN #{lat} - #{radius} / (6371000 * PI() / 180)
                      AND #{lat} + #{radius} / (6371000 * PI() / 180)
  AND s.longitude BETWEEN #{lng} - #{radius} / (6371000 * PI() / 180 * COS(RADIANS(#{lat})))
                      AND #{lng} + #{radius} / (6371000 * PI() / 180 * COS(RADIANS(#{lat})))
HAVING distance_meters <= #{radius}   -- 정확한 원은 여기서
```

- **조건은 `nearbyMode`가 아니라 `radiusMeters != null`로 건다.** 검색어+반경이 같이 오는 경우도 걸려야 한다
- `s.latitude IS NOT NULL` / `s.longitude IS NOT NULL`은 `BETWEEN`이 NULL을 배제하므로 중복이 된다
- XML에 NULL 가드 트릭을 설명하는 긴 주석이 있다. 형태를 바꾸면 **그 주석도 같이 고친다**

#### ⚠️ 상수 함정 — `111320`을 쓰지 말 것

흔히 쓰는 `111,320`은 **WGS84 적도 반지름 6,378,137**에서 나온 값인데,
이 쿼리의 `ACOS` 식은 **평균 반지름 6,371,000**을 쓴다. 기준이 어긋난다.

| 상수 | 유래 | 반경 3000m일 때 위도폭이 닿는 거리 |
|---|---|---|
| 111,320 | 적도 반지름 | **2,996.63 m** ← 3.37m 모자람 |
| 111,194.9 (`6371000*PI()/180`) | 평균 반지름 = 쿼리와 동일 | 3,000.00 m |

**사각형은 커도 무해하고(`HAVING`이 자른다) 작으면 버그다.** 작으면 반경 경계의 가맹점이
`HAVING`까지 도달하지 못하고 사라져 "결과가 안 바뀐다"는 A안의 전제가 깨진다.

### 3. 서비스 `DefaultStoreService` — 계단식 반경

```java
// 개념. 단계는 요청 반경으로 클램프 + 중복 제거
int[] steps = IntStream.of(300, 1000, R).map(s -> Math.min(s, R)).distinct().toArray();
for (int r : steps) {
    List<StoreSummaryResponse> found = storeMapper.findStores(cond.withRadius(r));
    if (found.size() == 5 && 마지막_거리 < r) return found;
}
return lastResult;   // 최대 반경에서도 5건 미만이면 있는 만큼
```

- **클램프 필수.** 사용자가 `radiusMeters=100`을 보내면 단계가 `[100]` 하나여야 한다.
  `[300, 1000, 100]`이면 요청보다 넓은 범위를 뒤져 명세를 어긴다
- **계단식은 `nearbyMode`에만.** 검색어가 있으면 `LIKE`가 먼저 쳐내 단계가 낭비다
  (실측: 스타벅스에 계단식을 걸면 0.05 + 0.12 + 0.49로 오히려 손해)
- **종료 조건은 "5건"이 아니라 "5건 && 5번째 거리 < 단계 반경".**
  5번째가 정확히 단계 반경에 걸치면 반경 밖의 같은 반올림 거리 행이 `store_rank`·`store_name`
  타이브레이크에서 앞설 수 있다
- `StoreSearchCondition`은 `@Setter` 금지라 `@Builder`로 새 인스턴스를 만든다(AGENTS.md §4)

### 4. 테스트

- **Service 단위** (필수, `@ExtendWith(MockitoExtension.class)`) — 계단식 루프: 5건 차면 멈추는지,
  요청 반경을 안 넘는지, 클램프·중복 제거, 5건 미만일 때 마지막 결과 반환
- **Mapper 통합** (필수, `@SpringJUnitConfig` + `@Transactional`) — bbox가 결과를 안 바꾸는지.
  단 로컬 dev DB는 `store`가 244건이라 성능은 확인 못 한다. **정확성만**
- 한 테스트에서 "조회 → 변경 → 같은 조회"를 하지 않는다 (AGENTS.md §12)

## PR 2 (검색어) — 이번 범위 아님

- FULLTEXT ngram 인덱스. `LIKE '%…%'` → `MATCH ... AGAINST(... IN BOOLEAN MODE)`
- **A+B와 성격이 다르다. 결과가 바뀐다** — 1글자 검색어는 `ngram_token_size=2`라 0건이 된다.
  최소 길이 정책이나 `LIKE` 폴백을 먼저 정해야 한다. **성능 작업이면서 검색 스펙 결정이다**
- **흔한 검색어로도 재야 한다.** 지금은 `LIKE`가 전건 스캔이라 매치 수와 무관하게 비슷하지만
  (스타벅스 24건 0.62s · 강남 6,377건 0.63s · 카페 35,759건 0.65s),
  FULLTEXT 후에는 갈라진다. `스타벅스`만 보면 "다 해결됐다"는 착시가 생긴다
- 인덱스가 크다 — 상호명 평균 6.6글자라 행당 항목 5.6개, 총 **약 1,515만 항목**
- 영어 검색: ngram은 언어를 안 가려 영어도 2글자씩 자른다. 콜레이션이 `utf8mb4_0900_ai_ci`라
  대소문자 무시도 유지된다. 다만 **데이터의 영문 비율이 2.9%**이고 `starbucks`는 **0건**,
  `스타벅스`는 24건이다 — 영어 검색이 안 되는 건 인덱스 문제가 아니라 데이터 문제다.
  `brand_alias` 테이블(V8·V9, 28행)이 이미 있으나 **앱 배선은 아직 없다**

## 노션 문서 형식 (PR 1 완료 후 정리할 골격)

사용자가 발표 자료를 만들 것을 전제로 **한 절 = 슬라이드 한 장**으로 잡기로 했다.
세부는 **토글**에 넣는다 — 토글이 곧 "발표에서 접고 질문 나오면 펴는 부분"이다.

```
0. 한 줄 결론      숫자 하나 (2.15s → 39ms)
1. 문제            SLO 위반 3건, 부하 시 23.6초
2. 진단            5건 뽑는데 272만 행. 왜 인덱스를 못 타는지
3. 후보와 trade-off  A~F 비교표 한 장
4. 선택과 근거      왜 A+B인가, 왜 E를 버렸나
5. 측정이 뒤집은 것  ↓
6. 적용하며 부딪힌 함정  ↓  ← 발표에서 가장 강한 절
7. 결과            전/후 표 + 측정 조건 명시
8. 남은 것          키워드 갈래 · 버퍼 풀 · 파라미터 편향
```

**5. 측정이 뒤집은 것** (지금까지 나온 것)
- bbox만으로 될 줄 알았는데 강남역 3km에 8.4만 개라 부족 → 계단식이 필요해졌다
- 카테고리가 없어질 줄 알았는데 살아있어서 → 인덱스가 1개에서 2개로
- 0.1초 목표를 잡는 순간 → 키워드 갈래가 선택에서 필수로

**6. 함정** (지금까지 나온 것)
- 위경도 인덱스를 **못 만드는 게 아니라** 쓸 조건이 없었다
- `111,320` vs `6371000·π/180` — 사각형은 커도 무해, 작으면 버그
- `NULL IS NULL OR` 트릭 위에 bbox를 얹으면 **결과는 맞고 성능만 조용히 죽는다**
- leftmost prefix 때문에 인덱스가 2개 필요하다
- `categoryId=1`이 7종 중 5번째로 작아 baseline 측정이 낙관적이었다

- 측정 파라미터가 **밀도는 최악(강남역), 나머지는 유리한 쪽**을 골랐다.
  `categoryId=1`은 158,235건인데 `기타`는 1,223,318건이고 로컬에서 0.24s 대 **1.76s(7.3배)**다.
  부하 테스트도 100 VU 전원이 **같은 좌표·검색어·업종·storeId**를 쳐서 버퍼 풀이 계속 뜨겁다
- `store` 테이블에는 **앱 쓰기가 전혀 없다**(Flyway 참조 데이터로만 채워진다).
  그래서 인덱스를 늘리는 대가가 저장공간뿐이다
- 사용자는 **이슈를 읽고 검토한 뒤 착수하는 것을 선호한다.** CLAUDE.md의 사전 승인 범위를
  그대로 연속 실행하지 말고 확인을 받는다
