# 7단계 최종 부하 테스트 — 설계

작성 2026-08-19 · 상태: 승인됨(구현 전)

> **한 줄 요약** — k6 시나리오의 좌표·검색어·카테고리·`storeId`가 전부 고정값이라 부하 테스트가
> 한 조합만 반복 측정하고 있었다. 데이터셋을 실사용 분포로 바꾸고, **개선 전 버전으로 되돌려
> 같은 하네스로 다시 잰 뒤**, 최신 버전으로 돌아와 최종 측정해 개선 폭을 보고한다.

## 배경 — 왜 다시 재는가

지금 `load.js`와 `baseline.js`는 아래 네 값이 하드코딩돼 있다.

| 값 | 현재 | 문제 |
|---|---|---|
| 좌표 | 강남역 `37.4979, 127.0276` | 272만 매장 중 최밀집 지점 하나만 잰다 |
| 검색어 | `스타벅스` (전국 24건) | 고유 검색어 305개 중 하나. 게다가 **가장 가벼운 축** |
| 카테고리 | `categoryId=1` (카페/디저트, 15.8만 행) | 7개 중 하나. 가장 무거운 `푸드`(67.0만)를 안 잰다 |
| `storeId` | `setup()`이 뽑은 첫 행 하나 | 전 VU가 같은 가맹점 |

유저만 활성 100명으로 다양하고(카드도 유저별), **가맹점 스코프 4종은 전부 한 점**이다.

그 결과가 5단계 설계에서 실제로 드러났다 — 「store/search 쿼리 최적화 2」 재측정에서
밀도 6단계 × 선택도 6단계로 넓히자 SLO 초과 경로가 4종 나왔고, 그중 어느 것도
k6가 쏘는 조합이 아니었다. **벤치마크 통과와 SLO 충족이 갈리는 지점이 측정에 안 잡힌다.**

## §1 데이터셋

### 산출물

`scripts/perf-k6/extract-scenarios.sh`가 **CSV 두 개**를 뽑는다. 목적이 다르므로 데이터셋도 나눈다.

| 파일 | 쓰는 곳 | 성격 | 행 수 |
|---|---|---|---|
| `scenarios-load.csv` | `load.js` (판정) | **실빈도 모사** — 실제 트래픽이면 버티나 | 2,000 |
| `scenarios-baseline.csv` | `baseline.js` (진단) | **층화 표본** — 어떤 조합이 얼마나 걸리나 | 40 |

`load.js`는 "우리 규모에서 서비스 가능한가"를 판정하므로 실제 분포가 맞고, `baseline.js`는
병목을 규명하므로 밀도 7단계가 고르게 들어가야 한다.

`scenarios-baseline.csv`가 40행인 것은 **예열 10회가 측정 표본을 미리 데우지 않게 하려는
것**이다. 앞 10행은 예열 전용이고 뒤 30행이 층화 표본이다 — 같은 행을 예열에 쓰면 그 조합만
버퍼 풀에 올라간 채로 측정에 들어간다.

**층화 기준**: 밀도 8단계(희소 앵커 `0` + 7분위수 `1~7`) × 검색어 선택도 3구간(전국 매칭 수
저 `< 1,000` · 중 `1,000~13,000` · 고 `> 13,000`)에서 뽑는다. 24칸에 30행이므로 각 칸 1~2행이고,
**두 경계가 반드시 들어간다** — 라우팅 임계값 13,000의 양쪽(#270의 계단/전국 분기)과,
`densityTier 0`(1km 안 0건, 사다리를 10km까지 올리는 유일한 경로)이다. **실빈도 표본이 밀집 좌표에 쏠려도
진단 표에는 희소 경로가 반드시 실린다** — 이것이 결정 3의 대가에 대한 보강이다.

### 지터가 필요한 이유, 그리고 지터로는 안 되는 것

매장 좌표를 그대로 쓰면 사용자가 항상 가맹점 위에 서 있게 되어 **300m 안에 최소 1건이
보장된다.** 그러면 계단식 반경이 언제나 첫 단계에서 끝난다. 지터는 그것을 푼다.

**그런데 지터로는 "1km 안에 매장이 없는 좌표"를 만들 수 없다.** 로컬 perf DB 272만 행에서
좌표 150개를 뽑아 지터 크기별로 1km 사각형 안 매장 수를 셌다.

| 지터 | 표본 | 1km 안 0건 | 5건 미만 |
|---|---|---|---|
| ±0.003° (±300m) | 150 | **0.0%** | 0.7% |
| ±0.010° (±1.1km) | 150 | **0.0%** | **0.0%** |

**1.1km까지 늘려도 한 건도 안 나온다.** 출발점이 매장인 한, 거기서 벗어나면 다른 매장이
또 있기 때문이다. ±1.1km에서 5건 미만조차 0%인 것은 지터가 희소 쪽으로 가는 만큼
밀집 쪽으로도 가기 때문이다.

그래서 지터는 **±500m**로 잡고(첫 단계 조기 종료만 풀면 된다), 희소 좌표는 따로 주입한다.

### 희소 앵커 주입 — 3%

`#270`의 고침 2(사다리를 3km·10km까지 올린다)는 **1km 안 0건 좌표**가 근거였다. 위 실측대로
그 좌표는 매장 밀도 가중 샘플링에서 구조적으로 배제되므로, **주입하지 않으면 그 설계 요소가
검증 없이 남는다.**

`scenarios-load.csv`의 **3%**(2,000행 중 60행)를 희소 앵커로 대체한다.

**왜 3%인가** — p95가 정확히 상위 5%다. 주입 비율을 5%로 잡으면 가장 느린 희소 좌표가
p95 경계에 정확히 앉아 **임의로 정한 손잡이 하나가 SLO 통과/실패를 결정한다.** 3%면 희소는
p97 바깥이라 전체 p95는 실사용 분포가 결정하고, **희소 구간은 밀도 태그의 자체 서브메트릭으로
따로 판정한다** — 밀도 태그를 넣은 이유가 원래 그것이다.

**앵커를 고르는 방법** — 매장이 있는 격자의 **이웃 중 비어 있는 격자**의 중심을 후보로 삼는다.
인접 격자에 가맹점이 있다는 것은 사람이 사는 곳이라는 뜻이라, 바다나 국토 밖으로 새지 않는
land proxy가 된다. 후보마다 **"1km 안 0건"을 실제로 검증**해 통과한 것만 쓰고, 한 지역에
몰리지 않도록 지리적으로 흩어 고른다. 지리산 `35.3370, 127.7306`은 5단계 재측정에서 이미
검증된 좌표라 시드 앵커로 포함한다.

희소 앵커에도 지터 ±500m를 동일하게 적용한다 — 반경 안이 여전히 비어 있어 성질이 유지된다.

### `storeId`를 CSV에 안 넣는 이유

같은 세션의 좌표 검색 응답에서 첫 가맹점을 이어받는다. 사용자의 실제 동선
(검색 → 가맹점 선택 → 결제 전 혜택 조회)과 인과가 맞고, 좌표가 바뀌면 `storeId`도
따라 바뀌어 두 값이 어긋나지 않는다. 화면 순서상 `검색`이 `결제 전`보다 앞이라 그대로 성립한다.
**0건이면** `setup()`이 미리 뽑아 둔 전역 값으로 폴백한다.

### 두 함정

**① 1글자 검색어는 after의 실패율을 오염시킨다.** #270이 2글자 미만을 400으로 거부하는데
k6의 `http_req_failed`는 4xx도 실패로 센다. before는 200, after는 400이 나와
"개선했더니 실패율이 올랐다"가 된다. 추출 SQL에 `CHAR_LENGTH(keyword) >= 2`를 건다.
(실측상 80만 건 중 1글자는 0건이라 방어적 조치다.)

**② `기타`(category 7)를 제외한다.** 매장의 45%를 차지하지만 **프론트 카테고리 칩에서
누를 수 없다**(2026-08-19 확인). 남은 6개가 재정규화되어 푸드 44.6% · 쇼핑 24.2% ·
편의점/마트 14.1% · 카페/디저트 10.5% · 병원 5.5% · 주유 1.0%가 된다.

### 어느 DB에서 뽑는가

**측정 대상인 운영 RDS에서 뽑는다.** 로컬 perf DB(3308)와 행 수가 같아 보여도 운영은
재적재 이력이 있어 동일성을 보증할 수 없다. k6 EC2에서 SSM으로 뽑는 것을 1순위로 하고,
경로가 없으면 로컬에서 뽑되 `store`·`search_history`의 행 수와 고유값을 운영과 대조한 뒤 쓴다.

두 CSV는 `active-users.csv`와 같이 **저장소에 커밋한다** — 두 측정이 같은 표본을 봤다는
근거가 파일로 남아야 한다.

## §2 하네스

### 조합 배정 — 난수를 쓰지 않는다

```js
const idx = (offset + (__VU - 1) + exec.scenario.iterationInInstance * VUS) % scenarios.length;
```

VU 100개가 매 반복마다 서로 다른 100칸씩 전진한다. 2,000행이면 20반복까지 겹침이 없고,
5분 ÷ 19.6초 ≈ 15반복이라 한 번도 재사용되지 않는다.

**난수가 없으므로 개선 전과 후가 같은 순서를 밟는 것이 구조적으로 보장된다** — 시드를 맞췄는지
확인할 필요조차 없다. 분포는 CSV가 들고 있으므로 순서대로 걸어도 실빈도가 깨지지 않는다.

`offset`은 워밍업에 `N/2`를 준다. 워밍업과 판정 구간이 같은 조합을 밟으면 판정 구간이 자기가
쓸 페이지를 미리 캐시에 올린 상태로 시작한다. 영향은 크지 않지만(버퍼 풀 5.25GB에 데이터
9.21GB) 공짜로 막을 수 있다.

`think time`의 무작위 지터는 그대로 둔다 — 목적이 VU 동기화 방지이고 평균이 같아 편향이 없다.

### `load.js` 변경점

1. `LAT`/`LNG` 상수와 하드코딩된 `%EC%8A%A4%ED%83%80%EB%B2%85%EC%8A%A4`, `categoryId=1` 제거
2. `url` 빌더 시그니처를 `(u) =>` → `(u, sc) =>`로 확장
3. `fire()`가 응답을 반환하게 하고, `store_search_coords` 응답의 첫 가맹점을 세션 상태에 담아
   `benefit_expected`가 이어받게 한다
4. **`setup()`의 "좌표 검색이 0건이면 중단" 검증은 폴백 프로브에만 남긴다.** 세션 좌표는
   희소 지역이 정상이라 0건이 실패가 아니다 — 그대로 두면 희소 좌표에서 테스트가 죽는다
5. `tags.name`은 지금처럼 고정 유지

### 밀도 태그

좌표 CSV의 `densityTier`를 요청 태그로 단다. 결과가 엔드포인트 하나가 아니라
**밀도 단계별로 갈린다.**

```
http_req_duration{name:store_search_coords, density:dense}
http_req_duration{name:store_search_coords, density:sparse}
```

"고정이라 무의미하다"의 반대편은 "흩뿌렸다"가 아니라 **"흩뿌린 결과 어느 구간이 어떻게
나오는지 보인다"**이다. 밀집에선 통과하는데 희소에선 실패한다면 그게 보고서의 핵심 발견이 된다.

> ⚠️ **k6는 임계값에 선언되지 않은 태그 조합의 서브메트릭을 만들지 않는다.**
> `handleSummary`에서 밀도별 수치를 읽으려면 통과가 보장되는 더미 임계값(`p(95)<999999`)이라도
> 걸어 서브메트릭을 실체화해야 한다. **빠뜨리면 에러 없이 밀도 표가 통째로 비어 나온다.**

### `baseline.js` 변경점

같은 방식이되 1 VU라 `scenarios-baseline.csv`를 반복마다 1:1로 밟는다(완전 결정적).
**예열 10회는 앞 10행, 측정 30회는 뒤 30행**이라 예열이 측정 조합을 데우지 않는다.
밀도 태그도 동일하게 단다 — 진단 스크립트라 여기가 밀도별 분해의 본진이다.

## §3 절차

되돌릴 수 없는 조작이 **운영 DB 인덱스 하나(V12 DROP)뿐**이도록 순서를 짰고,
끝났을 때 운영이 최신 상태로 남게 배치했다.

### Phase 0 — 준비 (배포 없음)

1. 추출 스크립트 작성 → 운영 RDS에서 두 CSV 생성 → 커밋
2. `load.js` · `baseline.js` 개조 → 커밋
3. **하네스 스모크** — 현재 배포된 버전 그대로 운영에 `baseline.js`를 N=5로 쏜다.
   확인할 것 셋: 조합이 실제로 갈리는가 · 밀도 태그가 요약에 실리는가 · `storeId` 인과가 도는가.
   로컬에 perf 데이터가 없어 로컬 재현이 더 비싸고, 실사용자 0명이라 운영에 30초 쏘는 게 무해하다
4. k6 EC2(`i-05eb81746a575ca47`)에 스크립트·CSV를 SSM heredoc으로 배포
5. **RDS에 SQL을 실행할 경로 확보** — V12 DROP/재생성에 필요하다.
   Phase 1에서 처음 발견하면 되돌리기가 중간에 멈춘다

### Phase 1 — 개선 전 만들기

6. **`search_history` 재적재 1회.** `store/keywords`가 `NOW() - 7 DAY`를 본다. 재적재하지 않으면
   집계가 0건이 되어 전·후 둘 다 빨라지고 비교가 무의미해진다. **이후 before/after 사이에는
   다시 건드리지 않는다** — 같은 데이터를 둘 다 보게 하려는 것이고, 몇 시간의 창 이동은
   80만 건이 7일에 흩어져 있어 무시할 수준이다
7. `DROP INDEX idx_search_history_searched_at_keyword ON search_history;`
8. EB 버전 라벨을 **`gh-283.1-4b6f6af`**로 변경 — 이미 EB에 있어 재빌드 없이 3~5분
9. **Flyway 기동 확인이 이 계획의 단일 최대 위험이다.** 이력에 V11~V13이 있는데 그 WAR은
   V10까지만 안다. Flyway 13은 `ignoreMigrationPatterns` 기본값이 `*:future`라 통과할 것으로
   보지만, 틀리면 **앱이 아예 안 뜬다.** EB 상태 · `GET /health/db` · 앱 로그(`/var/log/messages`)로 확인
10. 옛 코드가 실제로 도는지 육안 확인 — `store/search` 좌표 갈래가 초 단위로 돌아왔는지

### Phase 2 — before 측정

11. `baseline.js` N=30 → `baseline-before-*`
12. `load.js` 100 VU → `load-before-*`

1차 때와 같은 붕괴(SLO 0/19 · 5xx 45%)가 재현될 것으로 예상한다. **그건 실패가 아니라
예상된 결과다.** 다만 실패가 많으면 표본이 줄고 p95가 낙관적으로 나오므로, 보고서는 p95를
항상 달성 처리량·실패율과 함께 읽는다.

### Phase 3 — 복구 + 최신화

13. V12 인덱스 재생성 → **`SHOW INDEX`로 검증** (잊으면 after가 부당하게 느려진다)
14. PR #270 머지 → CD가 배포
15. V14 인덱스 생성 80초+ 대기 → EB 상태 · `/health/db` 확인
16. `SHOW INDEX FROM store`로 `ft_store_name` · `idx_store_lat_lng_name` 확인 +
    **stopword 검증**(`bar`의 LIKE 건수 == MATCH 건수). 어긋나면 영어 검색어가 조용히 0건이 되어
    after가 부당하게 빨라진다

### Phase 4 — after 측정

17. `baseline.js` N=30 → `baseline-after-*`
18. `load.js` 100 VU → `load-after-*`

### 규칙과 예산

## §4 보고서

**노션에 「7. 최종 부하 테스트」를 새로 만든다. 1차 결과 문서(4단계)는 건드리지 않는다** —
데이터셋이 달라 같은 표에 못 섞기 때문이고, 1차는 1차의 조건에서 유효한 기록으로 남긴다.

| 절 | 답하는 질문 |
|---|---|
| 1. 한 줄 요약 | 판정 |
| 2. 측정 조건 | 양쪽이 정말 같은 조건이었나 |
| 3. 1차 결과와 섞으면 안 되는 이유 | 데이터셋이 달라졌다 |
| 4. **1 VU 표** | 쿼리가 얼마나 빨라졌나 (엔드포인트별 배수) |
| 5. **100 VU 표** | 우리 규모에서 서비스 가능한가 (SLO 충족 · 에러율 · 처리량) |
| 6. **밀도별 분해** | 어느 구간이 어떻게 다른가 |
| 7. 한계 | 이 숫자를 어디까지 믿나 |
| 8. 남은 것 | |

### 서술 규칙

**"N배 빨라졌다"는 1 VU 표에서만 쓴다.** 100 VU의 before는 커넥션 풀 고갈을 잰 것이라 19개가
전부 3.00초에 붙어 있고, 손대지도 않은 `health_db`까지 74배 빨라진 것처럼 나온다. 인과는
맞지만(쿼리가 빨라져 풀이 안 마름) **엔드포인트별 배수로 읽으면 틀린다.**
100 VU는 시스템 수준 지표로만 말한다.

### 명시할 한계 여섯

1. **커넥션 풀 20을 바꾸지 않았다** — before의 100 VU는 쿼리가 아니라 풀 포화를 잰 값이다
2. **coordinated omission** — before는 실패가 많아 표본이 줄고 p95가 실제보다 낙관적이다
3. **희소 좌표 3%는 실사용 분포가 아니라 주입한 값이다** — 매장 밀도 가중 샘플링이 1km 안 0건
   좌표를 구조적으로 배제하기 때문이고(실측 0.0%), 그 비율 자체에는 근거가 없다.
   **희소 구간의 p95는 표본이 얇아 말하지 않는다** — 중앙값과 max로 읽고, 정밀 판정은
   1 VU 층화 표본이 담당한다
4. **밀도 단계는 `0.01°` 격자 근사**이지 반경 실측이 아니다
5. **1 VU는 N=30이라 p95를 말하지 않는다** — 중앙값과 max로 읽는다(perf-k6 README 함정 0)
6. **개선 전은 V12 인덱스만 되돌렸다** — V11·V13 잔존물은 옛 코드에 쓰는 SQL이 없어 영향 0이라는
   근거를 함께 싣는다
