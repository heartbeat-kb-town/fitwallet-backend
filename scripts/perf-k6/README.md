# 성능 고도화 — k6 측정 스크립트

| 스크립트 | 단계 | 무엇을 답하나 |
|---|---|---|
| `baseline.js` | 3단계 | **병목이 어디고 왜인가** — 부하 없이(1 VU) 엔드포인트별 순수 처리시간 |
| `load.js` | 4단계 | **우리 규모에서 서비스 가능한가** — 동시 사용자 100명에서 SLO 통과/실패 |

계획 문서가 3단계를 4단계보다 앞에 둔 이유는, baseline 표가 있어야 부하를 얹었을 때
늘어난 시간을 **경합 탓**으로 돌릴 수 있기 때문이다.

> **수치와 해석의 정본은 노션이다.** 이 저장소에는 도구만 둔다.
> 4단계 설계: 「SLI/SLO 정의 · 1차 부하 테스트 설계 (4단계)」

k6 run scripts/perf-k6/baseline.js

**같은 이름으로 덮어쓰므로** 보관할 결과는 `results/`로 옮겨 날짜를 붙인다.

### 어디서 돌리나

**k6는 k6 EC2(`i-05eb81746a575ca47`)에서 돌린다.** 로컬에서 쏘면 인터넷 왕복이 끼어
같은 조건이 아니다. `scripts/perf-k6/k6ec2.sh`가 전송과 실행과 결과 회수를 한다.

```bash
scripts/perf-k6/k6ec2.sh push
scripts/perf-k6/k6ec2.sh run load.js load-before-20260819 VUS=100
```

EC2 역할에 S3 권한이 없어 **presigned URL**로 주고받는다. IAM을 건드리지 않으려는 선택이다.

강남역 · `스타벅스` · 카페/디저트 · 단일 `storeId`. **한 조합만 반복 측정하고 있었다.**

다시 뽑지 않는다** — 두 측정이 같은 표본을 봐야 한다.

### 함정 5. 밀도 서브메트릭은 임계값을 선언해야 생긴다

k6는 임계값에 없는 태그 조합의 서브메트릭을 만들지 않는다. 밀도별 표를 읽으려면 통과가
보장되는 임계값(`p(95)<999999`)이라도 걸어야 한다. **빠뜨리면 에러 없이 표가 통째로 비어 나온다.**

### 함정 6. 지터로는 희소 좌표를 만들 수 없다

좌표를 `store`에서 뽑으면 출발점이 항상 가맹점이라, 지터를 ±1.1km까지 늘려도 **1km 안 0건이
0.0%다**(실측 150표본). 벗어나면 다른 매장이 또 있기 때문이다. 그래서 희소 앵커를 따로 주입한다 —
`#270`의 사다리 10km 확장이 그 좌표에서만 발동한다.

## 밟으면 조용히 틀리는 함정 다섯 개

전부 실제로 밟았고, 스크립트가 지금은 막고 있다.

### 0. 표본 30개로는 백분위를 말할 수 없다

처음 `READ_ITERATIONS=30`으로 재고 p95·p99를 표에 실었다. 상위 1% 구간의 표본 수를 세면 끝난다.

```
30 × 0.01 = 0.3개
```

**데이터가 없는 구간을 보간으로 지어낸 값**이고, 실측치가 정확히 그 모양이었다 —
p99가 언제나 max 바로 밑에 붙는다. 독립적인 정보가 아니라 max의 그림자다.

p95도 상위 5%에 1.5개뿐이라 사실상 "두 번째로 큰 값"이었다. **판정이 실제로 흔들린 지점이
하나 있다** — `store/keywords`를 p95 277ms로 SLO(300ms) 통과라고 적었는데 여유가 23ms뿐이었다.
N=200에서 266ms로 재확인해 이제 근거가 선다.

→ 기본값을 **200**으로 올리고 **p99는 결과 표에서 뺐다.** N=200에서도 상위 1%는 2개뿐이라
여전히 지어낸 값이다. **꼬리는 max로 본다.**

### 1. 활성 유저는 연속 블록이 아니다

`perf000001`은 거래가 **0건**이다. 활성 3만 명은 가입자 5만 명 전체에 흩어져 있다.

비활성 유저로 돌리면 집계 API가 전부 빈 응답을 20ms에 돌려주고, **0행 응답도 HTTP 200이라
에러율 0%로 초록불이 뜬다.** 표만 보면 "리포트 API는 이미 빠르다"로 읽혀 개선 대상에서 빠진다.
→ `setup()`이 리포트 요약이 비어 있으면 중단한다.

**활성 유저 목록을 문서에 박지 않는다.** 예전엔 `perf000100 · perf030001 · perf100000`을
적어뒀는데, 가입자를 10만 → 5만으로 줄이자 `perf100000`이 아예 없어졌다. 규모가 바뀔 때마다
낡는다. 기본값 `perf000100`만 실측으로 유지하고, 다른 유저가 필요하면 그때 찾는다.

```sql
SELECT u.login_id, COUNT(*) FROM payment_transaction pt
  JOIN user_card uc ON uc.user_card_id = pt.user_card_id
  JOIN users u ON u.user_id = uc.user_id
 WHERE pt.paid_at >= '2026-07-01' AND pt.paid_at < '2026-08-01'
 GROUP BY u.login_id ORDER BY 2 DESC LIMIT 5;
```

### 2. 어느 유저로 재는지가 수치를 좌우한다

**유저당 거래 수는 균등하지 않다.** 활성 유저 안에서도 연 89 ~ 7,052건으로 벌어진다(평균 904).
측정 월(2026-07)만 떼어 봐도 유저당 4 ~ 633건이다.

리포트·카드 계열은 유저 스코프 쿼리라 이 차이가 그대로 수치에 실린다. **표에 측정 유저를
함께 적지 않으면 다른 측정과 비교할 수 없다.**

> 이전 데이터는 활성 유저 전원이 정확히 180건으로 **분산이 0**이었다. 그래서 리포트 계열이
> p95 12ms로 나왔고 "병목이 아니다"로 결론냈는데, 쿼리가 빨라서가 아니라 훑을 행이
> 없었던 것이다. 자세한 내용은 노션 「데이터 적재 설계」 §14.

### 3. 활성 유저라도 카드 전부에 거래가 있진 않다

월 75건이 카드 여러 장에 흩어지므로 카드당 수십 건이다. `cards[0]`을 그냥 쓰면 카드 계열이
0행을 잴 수 있다. → `setup()`이 그 달 거래가 가장 많은 카드를 고른다.

### 4. `POST /api/cards/mydata`는 멱등하지 않다

컨트롤러 문서와 달리 호출할 때마다 카드가 늘어난다(한 세션에 2 → 6 → 11장).
`WRITE_USER`의 카드가 실행할 때마다 누적되므로 이 유저를 다른 측정에 재사용하지 않는다.

## READ와 WRITE를 나눠 재는 이유

34개를 한 목록에 넣고 똑같이 N번씩 돌리면 측정이 데이터를 부순다.

| 엔드포인트 | 반복하면 |
|---|---|
| `DELETE /store/keywords/recent` | 검색 이력을 통째로 지운다 → 이후 `GET /store/keywords`가 빈 결과를 잰다 |
| `POST /card` | `UNIQUE(user_id, card_product_id)`에 걸려 2회차부터 전부 실패 |
| `PATCH /user/payment-pin` | PIN이 바뀌어 이후 결제 계열이 전부 실패 |

그래서 READ(N=200, **SLO 판정의 정본**)와 WRITE(N=3, 전용 유저)로 나눈다.
**WRITE는 표본이 작아 p95를 신뢰하지 않는다** — p50과 max만 본다.
위 표의 세 엔드포인트는 아직 어느 쪽에도 넣지 않았다. 넣으려면 회차마다 상태를 되돌리는
`prepare` 훅이 필요하다.

# 4단계 — 1차 부하 테스트 (`load.js`)

## 실행

```bash
# ① 활성 유저 목록을 먼저 뽑는다 (RDS에서. 재적재할 때만 다시 하면 된다)
PERF_DB_HOST=<RDS 엔드포인트> PERF_DB_PORT=3306 \
PERF_DB_USER=<유저> PERF_DB_PASSWORD=<비번> \
  scripts/perf-k6/extract-active-users.sh

# ② 부하 테스트 (약 6분)
cd scripts/perf-k6 && k6 run load.js
```

결과는 `load-summary.md` / `load-summary.json`으로 떨어진다. **같은 이름으로 덮어쓰므로**
보관할 결과는 `results/`로 옮겨 날짜를 붙인다.

| 환경변수 | 기본값 | 설명 |
|---|---|---|
| `BASE_URL` | 운영 EB 주소 | 측정 대상 |
| `VUS` | 100 | 동시 사용자. **CSV의 유저 수보다 작아야 한다** |
| `RAMP` | `1m` | 워밍업 구간. 집계에서 제외된다 |
| `DURATION` | `5m` | 판정 구간 |
| `DURATION_SEC` | 300 | 달성 처리량 계산용. `DURATION`과 같은 값을 초로 |
| `THINK` | 3 | 화면 사이 평균 대기(초). 실제로는 1.5~4.5초로 흩뿌린다 |
| `USER_FILE` | `./active-users.csv` | 활성 유저 목록 |
| `PERF_PASSWORD` | `11112222` | 활성 유저 계정 비밀번호. `setup()`이 VU 수만큼 로그인할 때 쓴다 |

`MIN_TX`(기본 5) · `YEAR_MONTH` · `OUT`(기본 `./active-users.csv`)이다.

## 왜 동시 사용자 100명인가

계획 문서의 "300 TPS"는 근거가 없다 — 멘토 한 마디가 전부고 자체 역산은 약 15 TPS다.
TPS로는 유도가 안 되지만 동시 사용자 수는 역산된다.

```
DAU 5,000명 × 피크 시간대 방문 20% = 피크 1시간에 1,000명
1,000명 × (세션 3분 ÷ 60분)        = 동시 사용자 약 50명
```

측정은 그 **2배인 100명**에서 한다. 50명은 커넥션 풀(20)에 여유가 있어(11개 필요)
baseline과 비슷한 수치가 나온다. 100명은 22개가 필요해 **풀 상한을 넘는다** — 부하 때문에
새로 실패하는 항목이 여기서 드러난다.

대가: 판정 문장이 *"우리 규모에서 되는가"*가 아니라 **"우리 규모의 2배에서 되는가"**가 된다.

## 밟으면 조용히 틀리는 함정

### 1. 유저 한 명으로 쏘면 측정이 무효다

3단계는 `perf000100` 한 명으로 쟀다. 부하에서 그렇게 하면 그 유저의 행만 버퍼 풀에
눌러앉는다. 데이터 9.21GB가 버퍼 풀 5.25GB의 **1.75배**인데 **적중률만 100%로 나오는**
상태가 되고, 재산정으로 확보한 유저당 거래 편차 7.8배도 반영되지 않는다.
→ VU마다 CSV에서 다른 유저를 배정한다.

**유저를 흩뿌리는 것만으로는 부족하다 — 카드도 골라야 한다.** 활성 유저라도 보유 카드
전부에 거래가 있진 않아서(3단계 함정 3), `cards[0]`을 그냥 쓰면 카드 계열 4개
(`card_summary` · `card_transactions` · `card_usage` · `report_card_received`)가 **0행을 잰다.**
`setup()`이 유저마다 카드를 전부 훑어 **그 달 거래가 가장 많은 카드**를 고르고, 한 장도
거래가 없으면 중단한다. `baseline.js`와 같은 규칙이라 3단계 표와 4단계 표가 같은 데이터 양을
잰다 — 이게 어긋나면 "부하 때문에 새로 실패한 항목"을 가릴 때 경합 탓인지 데이터 양 탓인지
갈리지 않는다.

> 선정에 드는 비용은 유저당 3.9회 × 13ms ≈ 50ms인데, 대신 `payment_transaction` 전체를
> 집계하던 `user-cards?sort=RECENTLY_USED`(379ms)를 setup에서 안 쓰게 되어 **총 setup 시간은
> 오히려 줄어든다.** 그 엔드포인트는 여정에 그대로 있으므로 측정 대상에서 빠지지 않는다.

setup 로그가 선정된 카드의 거래 건수 분포(최소/중앙/최대)를 찍는다. **카드 계열이 빠르게
나왔을 때 "정말 빠른 것"과 "0행을 잰 것"을 사후에 가를 유일한 근거이므로 리포트에 함께 남긴다.**

### 2. `search_history`는 측정 당일에 다시 적재해야 한다

`store/keywords`가 `NOW() - INTERVAL 7 DAY`를 보는데 데이터는 고정 기준일로 만들어졌다.
**하루 지날 때마다 이 API가 저절로 빨라진다** — 기준일 +4일에 28% → 13.4%, +7일에 0%.
`verify.sql` §12가 벌어진 일수를 찍어 잡아낸다. 80만 행 41MB라 수 초면 된다.

### 3. think time이 없으면 VU 수와 사용자 수가 어긋난다

대기 없이 돌리면 VU 1명이 쉬지 않고 요청을 쏴서 실제 사용자 여러 명분이 된다.
그러면 위 역산(50명)과 연결되지 않아 "동시 사용자 N명"이라고 말할 수 없다.

### 4. VU 고정은 느린 응답을 과소 집계한다 (coordinated omission)

서버가 느려지면 VU가 응답을 기다리느라 요청을 덜 보낸다. **느린 응답이 지연시간 분포에
실제보다 적게 실린다.** 그래서 결과 표는 p95와 **달성 처리량**을 함께 찍는다 —
달성률이 낮으면 p95는 낙관적인 값이다.

덧붙여 **달성 처리량 자체가 실제보다 약 3% 높게 나온다.** k6의 `gracefulStop`(기본 30초)이 판정 구간
종료 후 진행 중이던 세션을 완주시키는데, 그 요청도 `phase:steady`로 집계되지만 분모(`DURATION_SEC`)는
늘지 않기 때문이다. 편향 방향이 항상 같으므로 **달성률이 100%에 가까워도 실제로는 그보다 낮다.**

`steady`에 `gracefulStop: '0s'`를 걸면 없앨 수 있지만 그렇게 하지 않았다 — 절단 시 취소되는
in-flight 요청이 `http_req_failed{phase:steady}`에 실려 **에러율 SLO(1%)를 최대 0.34% 잠식**한다.
진짜 합격/불합격 판정을 진단용 숫자 하나를 고치려고 오염시키는 것은 나쁜 거래다.
(`warmup` 쪽은 사정이 달라서 실제로 걸어 뒀다 — 함정 6.)

### 5. 램프업을 집계에 넣으면 p95가 흐려진다

워밍업(`ramping-vus`)과 판정(`constant-vus`)을 **별도 시나리오로 나누고** `phase` 태그로
구분한다. 임계값과 결과 표는 `phase:steady`만 본다.

### 6. `gracefulRampDown: '0s'`는 워밍업을 끊지 못한다

시나리오를 나눠도 **워밍업 VU가 판정 구간까지 따라 들어온다.** `gracefulRampDown`은 스테이지
사이 램프다운용이고, 시나리오 종료에는 `gracefulStop`(기본 30초)이 적용되기 때문이다.
여정 1회가 19.4초라 판정 시작 시점의 워밍업 VU는 사실상 전부 iteration 중간이고, 그대로 두면
**판정 구간 초반 부하가 최대 2배(200 VU)가 된다.** 그 요청 자체는 `phase:warmup`이라 표에서
빠지지만 **만들어내는 경합은 `phase:steady` 수치에 그대로 실린다** — p95와 에러율이 함께
비관적으로 오염돼 합격/불합격이 뒤집힐 수 있다.

부수 효과로 `__VU` 번호가 `1..N`이 아니라 흩어진 구간(실측 84~200)으로 잡혀
`load.js`의 모듈로 유저 배정이 깨진다 — 일부 유저가 두 VU에 중복 배정되고 일부 CSV 유저는
아예 안 쓰인다. 함정 1이 부분적으로 되살아나는 것이다.

`warmup`에만 `gracefulStop: '0s'`를 건다. 함정 4와 달리 여기서는 대가가 없다 —
잘린 요청의 태그가 `phase:warmup`이라 판정 메트릭에 실리지 않는다.

### 7. 실패한 요청은 지연시간을 **낮춘다**

k6는 실패 요청도 `http_req_duration`에 표본을 남긴다. 커넥션 에러는 **0ms**, 타임아웃은
타임아웃 시각으로. 실측하면 50ms 응답 20건에 실패 25건을 섞었을 때 중앙값이
**53.9ms → 10.8ms**로 내려간다. 실패율이 5%를 넘으면 p95까지 성공 표본의 낮은 분위수를
읽기 시작한다. **부하를 얹었는데 표가 baseline보다 빨라졌다면 개선이 아니라 이것을 의심한다.**

여기에 두 가지가 겹치면 조용해진다: ① 커넥션 리셋·타임아웃은 `status === 0`이라
**5xx만 세면 한 건도 안 잡힌다**, ② 임계값 위반은 k6 stdout과 exit code에만 나오고
`load-summary.md`에는 안 실린다. 그래서 결과 표에 **실패율**과 **커넥션 실패/타임아웃 건수**를
5xx와 따로 찍고, 실패가 0이 아니면 위 경고를 자동으로 붙인다.

> 커넥션 풀(20) 고갈은 `connectionTimeout=3000`에 걸린 500으로 나타난다는 것이 설계 §5의
> 전제인데, 그건 요청이 톰캣까지 도달했을 때 얘기다. accept 큐가 밀리거나 EB가 끊으면
> `status 0`이다. 둘을 나눠 세면 어느 쪽인지가 그대로 갈린다.
